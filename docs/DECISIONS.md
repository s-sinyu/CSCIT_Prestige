# Decisions log

One line per decision, as required by PRD section 0.3. "PO" = confirmed with the product owner.

## Changes from PRD v1.1 (confirmed with the product owner)

- **Database: PostgreSQL instead of MySQL 8.** The site is published on Render with a free hosted database (Neon PostgreSQL); free hosted MySQL options were less suitable. Flyway migrations, Testcontainers and SQL are written for PostgreSQL 16. (PO)
- **PRD 12.3 (MySQL on the owner's laptop, GitHub Codespaces) no longer applies.** The database is hosted on Neon; local development uses `docker-compose.yml`. The team develops on local machines, so no devcontainer is included. (PO)
- **Uploaded images are stored in the database** (`stored_files`, `bytea`) behind the `StorageService` interface, because Render's free disk is wiped on every restart. A cloud implementation can replace `DatabaseStorageService` without changing callers. (PO)
- **Strict BCE per user story.** Each user story has its own Boundary class (`boundary/*`, a `@RestController`) and Controller class (`control/*`, a `@Service`); entity classes in `entity/*` hold data and their own data-access methods (e.g. `Favourite.add(...)`), backed by Spring Data repositories. This replaces the PRD 7.1 package-by-feature layout. (PO)
- **All `[DEFAULT]` values in PRD section 15 are accepted as written.** (PO)
- **Test data:** a generator loads about 100 records per data type into the demo server through the `seed` profile; the `dev` profile loads a small set (10 per type). (PO)

## Implementation decisions (simplest option consistent with the PRD)

- Entities are wired to repositories once at start-up by `EntityRepositoryBinder`; unit tests bind Mockito mocks the same way.
- Integer ids use PostgreSQL `integer GENERATED BY DEFAULT AS IDENTITY` (Java `Integer`).
- Emails are stored in lower case; uniqueness is enforced case-insensitively by a unique index on `lower(email)`, including deleted accounts (email stays reserved).
- "One general rating per customer per designer" uses a PostgreSQL partial unique index (`WHERE project_id IS NULL`), plus a service-level check that returns 409.
- View de-duplication and idempotent favourites use `INSERT ... ON CONFLICT DO NOTHING` backed by unique constraints (safe under concurrency).
- Another designer's IDP, enquiry or rating owned by someone else returns **404** consistently (does not reveal that it exists).
- An IDP whose category was later deactivated may keep that category when edited; it cannot be moved into a different inactive category.
- Enquiry status: `NEW` may go straight to `REPLIED`; `READ -> READ` and `REPLIED -> REPLIED` are no-ops; any move backwards returns 400.
- Issue-report targets: the target IDP must exist and not be deleted; the target designer must be an interior designer. A `PLATFORM_ISSUE` report ignores any targets sent.
- Login of a suspended account returns 403 with a clear message; a deleted account gets the same 401 as a wrong password.
- A request with an invalid, expired, suspended or deleted user's token is treated as a visitor: public pages still work, protected endpoints return 401.
- `GET /api/categories` (active categories for dropdowns) returns a plain list rather than a page because it is small reference data.
- Search sort is chosen with `sort=newest|budgetAsc|budgetDesc` instead of raw property names.
- Public `ProjectDetail.favourited` is `null` for visitors and non-customers.
- The ratings response includes `mine` so a logged-in customer can edit or delete their own ratings from the list.
- Report "IDPs created" counts soft-deleted IDPs too (historical figure); top-10 ties are ordered by project id.
- Report CSV starts with a UTF-8 byte order mark so Excel detects the encoding; number cells are never prefixed.
- Image reordering (optional in FR-IDP-3) is not implemented; upload, delete and set-cover are.
- Hikari keeps no idle connections in `prod` so the free Neon database can scale to zero.
- Spring Boot 3.5.x / Java 21; React 18 + MUI 6 + Vite 5.
